## Context

Consumers pin flakeyard atoms in their `flake.nix`
([FY-0003](0003-repository-naming.md)) and want one update pull request per
input, not one pull request that updates everything. Every release of an atom
moves its tag `vX` ([FY-0007](0007-branching-and-releases.md)), and every
release within a major version is compatible
([FY-0006](0006-versioning-and-support.md)).

Probes with Nix 2.35.3 and Renovate 44.176.3, including full runs against a
local Forgejo that created real branches and pull requests, established:

- Renovate's `nix` manager reads `flake.lock`. It treats every input as a git
  reference without version semantics. For an input with `rev` in its URL, it
  proposes the current commit of the `ref` next to it and runs
  `nix flake update <input>`, which changes only that input's lock entry. An
  input without `rev` is updated only by lock file maintenance, which updates
  all inputs in one pull request.
- `github:owner/repo/<sha>` is updated to the head of the default branch, which
  for an atom is unreleased code and for nixpkgs is `master`, a branch without
  binaries in `cache.nixos.org`. `github:owner/repo/v1.2.3` and
  `github:owner/repo?ref=v1.2.3` are never updated. Nix rejects
  `github:owner/repo?ref=v1&rev=<sha>`.
- `git+https://github.com/owner/repo?ref=v1&rev=<sha>&shallow=1` is accepted by
  Nix and gives one pull request per input whenever `v1` moves. Nix fetches by
  `rev` and does not check that it belongs to `ref`; without `rev`, a bare tag
  name in `ref` fails, because Nix looks for a branch. The lock entry has the
  same content hash as the `github:` form; fetching costs a fraction of a second
  more per input.
- Renovate resolves `ref` with `git ls-remote`, which lists branches before
  tags: a branch named `v1` takes precedence over the tag `v1`.
- Renovate cannot update `ref` and `rev` together, so it cannot propose a new
  major version. Its pull requests show the old and new commit only, without a
  version or release notes.
- When `flake.nix` and `flake.lock` disagree, `--no-write-lock-file` silently
  uses `flake.nix`; only `--no-update-lock-file` fails.

## Decision

### Form

Every flake input in flakeyard repositories and in projects generated by
flakeyard templates is written as

```nix
url = "git+https://github.com/<owner>/<repo>?ref=<ref>&rev=<commit>&shallow=1";
```

where `ref` is:

- for flakeyard repositories, the moving tag of the major version, such as `v1`;
- for nixpkgs, the channel branch, such as `nixos-unstable`;
- for upstream flakes without releases, such as treefmt-nix, git-hooks.nix and
  flake-parts, their default branch.

`ref` tells Renovate what to follow; Nix ignores it and fetches `rev`.

### Updates

Renovate proposes one pull request per input whenever its `ref` moves. Lock file
maintenance is off. The flakeyard Renovate preset adds to every such pull
request a link to the comparison of the two commits and to the releases page.
Since flakeyard squash-merges pull requests with Conventional Commits titles,
that comparison is the list of changes.

All updates of an atom within one major version are compatible, so they may be
merged automatically when checks pass. Major versions are never proposed by
Renovate: the last minor release of a major version, released just before the
first breaking change is merged, warns during evaluation that the next major
version is coming, that support ends 6 months after its first release, and where
the migration guide is.

### Verification

CI evaluates with `--no-update-lock-file`, so `flake.nix` and `flake.lock` must
agree. `action-flake-lock` checks that the `rev` of every flakeyard input is the
commit of a release tag `vX.Y.Z` of the major version named by its `ref`.
Branches named like release tags are forbidden by organization settings, so
`ref` always resolves to the tag.

### Revisiting

This decision is revisited when Renovate's `nix` manager can replace `ref` and
`rev` together: pull requests could then carry versions, release notes and major
updates. The proposal is tracked in
[renovatebot/renovate#47309](https://github.com/renovatebot/renovate/discussions/47309).

## Constraints

- Flake inputs in flakeyard repositories and in generated projects MUST use the
  form `git+https://github.com/<owner>/<repo>?ref=<ref>&rev=<commit>&shallow=1`
  with the `ref` defined in this decision.
- `ref` of a flakeyard input MUST be its moving major tag `vX`.
- CI MUST evaluate flakes with `--no-update-lock-file`.
- `action-flake-lock` MUST fail when the `rev` of a flakeyard input is not the
  commit of a release tag `vX.Y.Z` whose major version matches its `ref`.
- Rulesets MUST forbid creating, updating and deleting branches whose names
  match `v[0-9]*`.
- The Renovate preset MUST disable lock file maintenance and major updates of
  flake inputs, and MUST add the comparison link to their pull requests.
- The last minor release of a major version, released before the first breaking
  change of the next one is merged, MUST emit the warning described in this
  decision. Atom READMEs MUST show inputs in this form.

## Consequences

- (+) One pull request per input and release, created and locked by Renovate
  without manual steps.
- (+) nixpkgs follows its channel, where `cache.nixos.org` has binaries.
- (+) Fetching goes through git, so it is not limited by the GitHub API.
- (−) Pull requests show commits instead of versions; automerge rules cannot
  tell a patch from a minor release.
- (−) Major versions need a manual change of `ref` and `rev`, prompted only by
  the warning.
- (−) URLs are longer than the `github:` form, and `ref` without `rev` does not
  work, which may surprise people who edit them by hand.
- (±) Consumers may use other forms, but lose per-input updates.

## Alternatives considered

- **`github:owner/repo/<sha>`.** Shortest, but Renovate updates it to unreleased
  code and nixpkgs to `master`.
- **Exact tags (`github:owner/repo/v1.2.3`).** Readable and immutable, but never
  updated by Renovate.
- **Exact tags with a custom regex manager.** Pull requests with versions,
  release notes and release ages, but the lock file is not updated without
  post-upgrade commands, which only self-hosted Renovate runs.
- **`github:` inputs without `rev` and lock file maintenance.** One pull request
  for all inputs, and failures cannot be attributed to one of them.
- **FlakeHub.** Server-side version ranges, but no Renovate support and a
  dependency on one more service.
