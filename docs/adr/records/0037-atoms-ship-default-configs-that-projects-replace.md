## Context

Atoms own the linters and formatters of their domains
([FY-0017](0017-atom-contract.md)). Most of these tools read a configuration
file, and flakeyard needs one configuration of each tool for its own
repositories. Projects that use the atoms need their own: a different set of
rules, a stricter or looser profile, a tool option flakeyard does not use.
FY-0017 lets a project override any module option an atom sets, but a
configuration file is the form in which people, editors and the tools'
documentation express a configuration.

Reading the tools and git-hooks.nix showed:

- actionlint, zizmor and most other tools read exactly one configuration file,
  found by discovery or named by a flag. None of them merges two files.
- Discovery depends on where the tool runs. actionlint looks for
  `.github/actionlint.yaml` only in a directory that contains both
  `.github/workflows` and `.git`. The check of a domain runs in the Nix sandbox
  over the files of that domain and has no `.git`, so actionlint there would
  ignore the project's file silently while the git hook in the working tree
  would honour it.
- A check that reads a file as `${self}/<path>` depends on the whole source of
  the project, so any change rebuilds it, and the check of an untouched domain
  is no longer substituted ([FY-0019](0019-binary-cache.md)).
- Tools differ in how a configuration reaches them: some take a file by flag,
  shellcheck takes only flags or a `.shellcheckrc` found next to each script,
  shfmt reads `.editorconfig` only when no formatting flags are given,
  editorconfig-checker has no configuration besides `.editorconfig`, and nixfmt,
  deadnix and reuse have no configuration file at all.
- `.editorconfig` is read by the tools of several atoms: text, shell, markdown
  and data formats.
- [FY-0024](0024-versioning-and-support.md) requires that a check, hook or rule
  that could fail a project that passed before ships disabled in a minor
  release. A stricter default configuration is such a rule.
- A pull request that adds a configuration file can switch off a check, and the
  required check of
  [FY-0034](0034-check-every-repository-with-workflow-check.md) stays green.

## Decision

### Defaults

The atom that owns a tool ships flakeyard's configuration of that tool in its
`config/` directory. It is the configuration of the organization: flakeyard's
repositories use it, and projects get it unless they replace it.

### Replacement

A project replaces the default of a tool by committing its own file at the
tool's standard path at the root of the project, such as
`.github/actionlint.yaml` or `.github/zizmor.yml`. The project's file replaces
the default wholly; nothing is merged. The atom detects the file at evaluation
with `builtins.pathExists` on the project's source, which for a git flake
contains only tracked files. Only the standard path at the root is detected;
files in subdirectories behave as the tool defines.

Every value the atom sets also stays a module option that a plain definition of
the project overrides (FY-0017).

### Explicit configuration

The atom never relies on the tool's own discovery. It passes the chosen file,
its default or the project's file, by the tool's flag, such as `-config-file` or
`--config`. The chosen file enters the check of the domain as a store path of
its own, with `builtins.path`, and is part of that check's inputs, so a change
of the configuration rebuilds the check and a change elsewhere does not.

### Kinds of tools

Each atom's README has a table with one row per tool: the standard path, how the
default is delivered and what the project's file does. The kinds are:

- **A file by flag** (actionlint, zizmor, statix, gitleaks, lychee, commitlint,
  markdownlint and the YAML and TOML formatters): as described above.
- **Flags only** (shellcheck): the atom passes its defaults as flags when the
  project has no file at the standard path, and none when it has one, so the
  project's file alone applies.
- **Configured by `.editorconfig`** (editorconfig-checker, and shfmt, prettier
  where they read it): no default from the atom. `.editorconfig` is a file of
  the project, generated by the templates; atoms list it among the files they
  read.
- **No configuration** (nixfmt, deadnix, reuse): nothing to replace.

When a tool still reads discovered files despite an explicit flag, the atom's
README says so, and a fixture of the atom asserts the behaviour the README
describes.

### Tools run by other tools

A tool that another tool runs, such as shellcheck inside actionlint for `run:`
blocks, is a dependency of that tool and has no second owner. The atom passes it
by its store path from the consumer's `pkgs`; the configuration of the atom that
owns it does not apply there.

### Changing a default

A change of a default configuration is part of the atom's public API (FY-0017,
FY-0024):

- A looser default is a minor release.
- A stricter default ships first in a minor release as an opt-in file
  `config/next/<file>` that a project may select, with an evaluation warning
  that it becomes the default in the next major version. The next major version
  makes it the default.
- A stricter result caused by a new version of a tool in the consumer's nixpkgs
  is not a change of the atom (FY-0024).
- Releases `0.y.z` are previews without guarantees (FY-0024) and may change a
  default in any release.

### flakeyard's repositories

flakeyard's repositories keep no configuration files of atom tools. Exceptions
are inline comments where the tool supports them, such as
`# zizmor: ignore[<audit>]` or `# shellcheck disable=<code>`, which a reviewer
sees in the diff. `workflow-check` fails a check of a flakeyard repository that
adds such a file, through an input that flakeyard's repositories switch on.

## Constraints

- The atom that owns a tool MUST ship flakeyard's configuration of that tool in
  `config/`, when the tool has a configuration file or flags to configure.
- A project's file at the tool's standard path at the root MUST replace the
  default wholly. Atoms MUST NOT merge configuration files.
- Atoms MUST pass the chosen configuration to the tool explicitly and MUST NOT
  rely on the tool's discovery of configuration files.
- The chosen configuration file MUST be an input of the check of its domain as a
  store path of its own. A check MUST NOT depend on the whole source of the
  project to read a configuration file.
- Every atom README MUST list, per tool, the standard path, how the default is
  delivered and what a project's file does.
- Atoms MUST NOT ship `.editorconfig`; it belongs to the project.
- A tool run by another tool MUST be passed by its store path from the
  consumer's `pkgs`.
- A stricter default configuration MUST first ship in a minor release as an
  opt-in under `config/next/` with an evaluation warning, and MAY become the
  default only in the next major release.
- flakeyard's repositories MUST NOT contain configuration files of atom tools.
  Exceptions MUST be inline comments.
- `workflow-check` MUST offer a check that fails on configuration files of atom
  tools, and flakeyard's repositories MUST switch it on.

## Consequences

- (+) A project changes a tool's configuration the way the tool documents it,
  and editors see the same file.
- (+) The check of a domain reads exactly the configuration it was built with,
  in CI and in the git hook, and is rebuilt only when that configuration or the
  domain's files change.
- (+) flakeyard's repositories share one configuration per tool, with no copies
  ([FY-0035](0035-extract-logic-that-has-two-users.md)).
- (−) A project that wants one rule changed copies the whole default and no
  longer receives changes of it.
- (−) An untracked configuration file is seen by the tool in the working tree
  but not by the check until it is committed.
- (−) Each atom maintains its table of tools and fixtures for both cases.
- (±) A stricter default takes two releases: an opt-in in a minor release and
  the switch in the next major release.

## Alternatives considered

- **Merging the project's file over the default.** The tools cannot merge, so
  flakeyard would define a schema of its own per tool, which FY-0017 rejected.
- **Module options only.** Explicit, but editors and people do not see the
  configuration, and the owner asked for files.
- **The tools' own discovery.** Silently ignores the project's file in the
  sandbox for tools that need `.git`, and ties checks to the whole source.
- **Defaults only, overridden with `mkForce`.** Does not let projects use their
  own configuration files.
